C3 v2.63.0 · Mask Guard

Show the file. Control what it says.

Access Guard answers may the agent touch this path? Mask Guard answers a different question — what should it see when it does?

A masked file stays visible, searchable, and useful. But every byte the AI receives comes from a transformed copy built once and stored outside your repo. Your actual file is never touched, never moved, never rewritten.

What it actually looks like

Three files, three kinds of protection

your file — customers.csv
id,name,email,plan
1,Ann Chen,ann@acme.io,pro
2,Bo Diaz,bo@acme.io,free
3,Ann Chen,ann@acme.io,pro
what the AI sees
id,name,email,plan
1,name_ed4835db4d,email_8a3b58ddf6,pro
2,name_198f140406,email_35eb9269cd,free
3,name_ed4835db4d,email_8a3b58ddf6,pro

Look at rows 1 and 3. Both are Ann Chen, and both get the same pseudonym — so joins, duplicates and cardinality all still work. The AI can reason about the data's shape without ever holding a real name. The mapping is one-way and salted per project; there is no reverse dictionary anywhere for someone to steal.

your file — settings.py
AWS_KEY = "AKIAIOSFODNN7EXAMPLE"
DB_PASSWORD = "hunter2-long-secret"
DEBUG = True
what the AI sees
AWS_KEY = "«c3:redacted:aws_access_key»"
DB_PASSWORD = «c3:redacted:secret»
DEBUG = True

The secrets are gone but the structure survives — the agent still knows those settings exist and that DEBUG is on. Those placeholders are spelled with guillemets on purpose: they're not valid syntax in any language, so if one ever ended up in a real file, your linter trips instead of the value getting quietly committed.

your file — vendor/sdk.py
def connect(host, port=443):
    secret_sauce = compute(host)
    return secret_sauce * 2
class Client:
    def send(self, payload):
        return payload
what the AI sees
def connect(host, port=443)

class Client
  def send(self, payload)

Not everything you mask is a secret. A vendored SDK served as signatures only is also a large token saving — the agent gets the API surface it needs to call things correctly, and none of the body text it was going to waste context on.

The four transforms

Pick a preset, point it at a glob

There's no scripting language and no AI in the read path. Every transform is a named, versioned function, so the same file renders identically on every read and through every tool — which is what stops an agent from reconstructing the original by comparing one tool's output against another's.

redact_secrets Finds AWS / GitHub / OpenAI / Slack keys, JWTs, private keys, connection strings and password assignments — plus a high-entropy sweep — and replaces the values. Surrounding code stays readable. no arguments
redact_columns Swaps named CSV/TSV columns for stable pseudonyms. Same value always maps to the same pseudonym, so relationships in the data survive intact. columns=email,full_name
sample_rows Keeps the header plus N rows, and states how many were withheld — so the agent can't mistake a sample for the whole dataset. count=20 · strategy=first|last
signatures_only Declarations and signatures, no bodies. Reuses C3's existing compressor, so it doubles as context compression. no arguments
Where it sits

One more rung on the ladder you already had

deny Invisible. No read, no write, not even listed in search results.
mask Visible and searchable, but transformed — and always read-only. New.
read_only Fully readable, but the agent can't change it.

When more than one applies, the strictest wins: deny beats mask beats read_only.

Three things worth knowing

The parts that might surprise you

Masked always means read-only. There's no override.

The agent read a transformed file, so any edit it proposes is written in transformed coordinates. Cropped rows have no way back. It might invent an identifier that doesn't exist in your file. A half-copied placeholder would get written verbatim — silently corrupting the one file you cared enough to protect. Translating those edits back "usually works", and that is precisely what makes it dangerous.

Adding a rule isn't enough — you have to activate it.

Before you masked that file, C3 had already read it. Its content sits in the compression cache, the search index, file memory, and possibly in auto-memory facts. A new rule doesn't retroactively clean any of that, so activation purges all of it, then builds and validates every view. Until that finishes, the UI banner and c3 access mask status both tell you masking is not in effect yet.

One-time cost: facts written before v2.63.0 have no record of which file they came from, so they can't be proven clean. Your first activation in a project clears them. Anything you stored by hand is untouched.

This is context hygiene, not containment.

The real bytes never leave your disk. Your editor sees them, a raw shell sees them, git sees them, and any non-C3 agent sees them. Mask Guard governs what reaches the model through C3 — and it says so plainly in the coverage matrix rather than implying more. If a file must never be readable at all, that's still deny.

Using it

Five commands

Everything here is also in the UI: Access Guard tab → + Add mask, with a live before/after preview on the path probe so you can see exactly what the agent will see before you commit the rule. 

# add a rule (--global applies it to every project)
c3 access mask add "data/**" --preset sample_rows --params "count=20,strategy=first"

# see what the agent will see, on your real file
c3 access mask preview data/customers.csv

# purge pre-mask caches and build the views — required
c3 access mask activate

# is masking actually in effect right now?
c3 access mask status

# stop masking (the agent gets the real contents back)
c3 access mask rm "data/**"
